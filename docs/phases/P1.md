## Outcome

P1-A establishes an evidence-backed capability matrix for Taobao/Tmall, JD, and Pinduoduo and a candidate technology version set. ## Development strategy adjustment

Decision date: 2026-09-13

> 真实平台 API 接入暂缓，当前开发阶段使用可替换的 Mock 商品数据，不改变未来 Platform Adapter 架构。

This decision does not convert P1-A research findings into account authorization and does not make P1 fully complete. Current Mini Program development may use clearly labelled, deterministic product and offer fixtures behind the service boundary. No real platform API, credential, promotion link, payment, order, or logistics capability is enabled by this change.

The Mock catalog is an interim development data source. Pages must consume platform-neutral service contracts and must not import fixtures or models directly. Replacing the source later with Spring Boot, MySQL, and approved Platform Adapters must preserve those page-facing contracts.

ADR-0001 formally permits P2 through P5 to proceed without live platform credentials. This is a sequencing change, not a waiver of P1 evidence. P6 remains blocked until the selected platform passes the formal authorization, live-interface, promotion-conversion, and physical-device jump gates.

The existing 30-product and 90-offer Mock Catalog is early technical validation only. It does not complete P4 domain/database acceptance or P5 OpenAPI/Mock Adapter acceptance. P4 must review it against the approved `UnifiedProductOffer` model; if they conflict, the Mock implementation must change to match the formal model.

The current recommended onboarding order is:

1. **Pinduoduo / Duoduo Jinbao** — the official material explicitly supports API/SDK integration for Mini Programs and WeChat scenarios. Exact current API entitlements, quotas, and target Mini Program parameters still require account and device validation.
2. **JD Union / JOS** — the public official capability description is complete for category, search, detail, coupon, link conversion, and Java SDK. A compliant direct WeChat Mini Program purchase path is not publicly proven.
3. **Taobao/Tmall / Taobao Alliance** — search, detail, coupon, and conversion APIs are documented, but consumer price-comparison scenarios have additional permission boundaries and the documented Mini Program link field is not publicly open.

This is a research priority, not a final platform selection. P6 must use the platform that first passes the full P1 account and real-device gates.

## Compliance risks found in P1-A

| Risk | User/product impact | P1 disposition |
|---|---|---|
| Public API docs do not grant this operator access | Search, detail, or conversion may fail after implementation | Require redacted account permission evidence before coding a real adapter |
| Numeric quotas and product-data retention terms are not public-confirmed | Aggressive caching/sync could breach terms or produce stale prices | Keep plan retention values provisional; obtain console/agreement evidence |
| Price and coupon fields are entitlement- and time-dependent | Users could see a price they cannot obtain | Later UI/API must expose observed time and conditions and refresh before jump |
| Commission-bearing links and ranking can influence results | Hidden commercial bias harms user trust and may create disclosure risk | Preserve source/price provenance and require explicit ranking/disclosure review |
| WeChat's generic jump API does not prove target-platform permission | A built purchase button could fail review or fail on-device | Do not approve a route until the platform account supplies the target and physical-device tests pass |
| Pinduoduo public API evidence is dated 2020 | Current field names, permissions, or SDK support may have changed | Treat current schema, quota, and Java SDK as account-validation items |
| Regulated/blocked categories differ by platform and Mini Program context | Disallowed goods could be displayed or routed | Use official allow/deny data and retain a platform kill switch in later phases |
| SDK and database/cache licenses vary by artifact/deployment | Redistribution or hosted use could create notice/source obligations | Capture exact artifacts and approve notices/deployment mode before adoption |

## Conditions still required for full P1 PASS

P1 cannot pass until all of the following are evidenced:

1. The operator completes the application/identity/media registration required by each platform and provides redacted approval evidence.
2. The live consoles confirm enabled APIs, response fields, quotas/rate limits, callbacks, product scope, and data-retention terms for each account.
3. At least one approved test account completes live search, detail, and promotion conversion without exposing credentials.
4. At least one platform completes a permitted purchase jump on a physical WeChat device, including failure/fallback evidence.
5. Exact SDK artifacts, versions, checksums/provenance, and licenses are captured after permissions are granted.
6. Redis 8 license/deployment mode, MySQL/Connector/J distribution model, and all third-party notices are formally approved and saved.
7. The candidate version set is reproduced in an isolated environment and pinned by exact source commit/image/artifact versions.

P1-A stops here. P1-B is deliberately deferred because it depends on external account and device conditions. P2 has not started, but may now start under ADR-0001 without claiming P1 overall completion.
